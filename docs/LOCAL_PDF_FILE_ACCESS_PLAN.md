# Local PDF access with settings closed

Approved scope, 4 November 2026: add optional local file URL access. Keep all PDFs local, preserve original bytes, exact server-authorized filenames and existing Manager/browser/job/attempt checks. No rendering, cloud storage, database changes or new manifest permissions.

Chrome's user-controlled **Allow access to file URLs** is broader than a directory grant. QTS must restrict its reads to an explicitly configured absolute Windows `QTS_Resume` directory and exact relative PDF paths returned by the existing documents authorization endpoint. This is one configuration per Chrome profile, not a promise that Chrome permissions cannot be revoked.

Final safeguards: direct mode hides inactive picker warnings so they do not imply it needs a directory grant. ## Acceptance criteria

- An authorized Manager explicitly configures the local folder, then normal Apply and Auto Apply can upload the original PDFs without a settings tab.
- A complete browser restart retains configuration; disabling file URL permission produces actionable, retryable failure without prompting or rendering.
- Unauthorized documents responses cause zero local reads. Invalid paths cause zero file fetches. No path or PDF bytes are added to backend requests.
- Existing picker configuration remains intact, can be selected again, and continues to support explicit legacy recovery.
- No deployment, migration or production data changes are needed. Commit/push is separate from this implementation and validation.

## Setup after updating the unpacked extension

The QTS > Tools > Apply PDFs folder entry opens a compact setting inside the QTS panel. That view intentionally exposes only the shared QTS_Resume folder picker and permission restoration; it does not show direct-file setup or legacy PDF relinking. The detailed direct-file steps below apply only when opening the full extension settings page directly.

1. Reload QTS at `chrome://extensions`. For an unpacked installation, keep Developer mode enabled.
2. Open QTS Details and enable **Allow access to file URLs**. Chrome may reload the extension when this setting changes; refresh an existing job tab if its old extension controls stop responding.
3. Open QTS > Tools > Apply PDFs folder. Under **Use PDFs with settings closed**, enter the full actual Windows path ending in `QTS_Resume` (for example `C:\Users\YourName\Downloads\QTS_Resume`, without surrounding quotes).
4. Choose **Save local PDF access** and confirm **Configured**. This records the folder; exact file availability is checked per job during Apply. Close settings and use Apply or Auto Apply. If an existing normal Apply review is paused, choose **Retry autofill** explicitly.
5. To revert, choose **Use folder picker instead** and check the saved directory permission below. The old handle is not deleted. Legacy jobs that need manual PDF relinking require this explicit mode switch, picker access and confirmation, ensuring Retry uses the reviewed directory. Returning to direct mode is an explicit setup action. Direct-file mode never enumerates or guesses files.

The new mode is Windows-only and intentionally excludes UNC/network/device roots. Each Chrome profile needs its own initial configuration/Chrome switch, but can point to the same trusted physical directory. Moving the directory or revoking the Chrome switch requires an explicit setup correction. Path containment is lexical: fetch cannot inspect Windows junctions/symlinks, so use a trusted ordinary local directory. Files are read on demand; PDFs are not copied into IndexedDB or sent to Vercel.
