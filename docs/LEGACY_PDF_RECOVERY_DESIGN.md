## Verified problem and existing boundaries

Migration `0088_curly_payback.sql` adds nullable `jobs.cover_letter_local_path` without a backfill. `loadApplyDocumentPaths` in `src/server/apply/apply-documents.ts` returns neither document unless both job paths exist and a delivered Generation run exists. Generation finalize now records Chrome's exact completed download paths, but old rows do not acquire that information retrospectively. Generation queue/start and completed-job guards prevent using Generation as a recovery mechanism.

The documents route currently authenticates Manager Apply access, registered browser identity/version, attempt Manager/browser ownership, allowed status (`claimed`, `waiting_review`, `submitting`), and a delivered run. Its query does **not** explicitly test lease expiry or current job Manager ownership; the comment calling it a live claim is stronger than the implementation. Recovery must add its own complete write authorization; it must not treat a documents 404 as permission to edit a job. Keep this endpoint and its existing checks.

`claimJobForBrowser` already accepts a completed job with a resume path, no existing bid, and no live claim, without requiring a cover-letter path. Therefore an eligible legacy job can enter an ordinary owned Assisted Apply attempt and pause on the missing metadata. No expansion of completed-job or Generation eligibility is needed. Not every historical completed row is necessarily eligible: bids, applied status, candidate availability, or another profile's live claim can prevent entry.

The existing local reader uses `applyPdfDownloadsDirectoryV1` in the extension's IndexedDB, requires a granted read permission, and walks exact `QTS_Resume/...` paths. It never searches for substitute filenames. The older `generatedResumeLocalPath` helper also documents a flat `QTS_Resume/<candidate>_Resume.pdf` layout; recovery must not assume every legacy folder has today's Manager/candidate/timestamp structure.

## Options considered

| Approach | Advantages | Problems / decision |
| --- | --- | --- |
| Derive the cover-letter name from the resume path or current Generation naming rules; SQL backfill | Small apparent change | Cannot identify Chrome suffixes, historical names, or the correct existing file. Reject. |
| Search Downloads or this profile's Chrome download history and choose a match | Can suggest candidates | History is profile-specific and may be cleared; multiple downloads can match. Automatic choice violates exact-file confirmation. Do not build a discovery/history subsystem. |
| Keep per-profile recovery overrides only in IndexedDB | No server write | Does not repair shared metadata, requires repeating selections in every profile, and adds a second source of truth to the authorized documents flow. Reject for shared recovery. |
| Native file picker for each role, then resolve each selected handle relative to the authorized Downloads handle | Explicit actual-file selection; supports suffixes | Viable, but adds user-gesture handling, extra file grants, and containment checks; `startIn` is only a starting location. Larger than needed for files already in a granted folder. Defer arbitrary-folder relocation. |
| Explicitly select both real entries in the job's recorded folder; save the confirmed relative paths once | Uses the existing read-only handle, no new filesystem grant; works across profiles through shared metadata | Recommended. Requires Manager review because historical byte fingerprints do not exist. Limits recovery to the already recorded folder. |
| Regenerate, rerender, or upload PDFs to Vercel for matching | None needed for this task | Violates byte-reuse requirements or adds document transfer/storage and rendering work. Reject. |

The recommendation is an authorized manual relinking workflow on the existing top-level `extension/settings/apply-pdfs.html` page. Add a job-specific mode rather than a new page or a new legacy feature. Chrome supports enumerating an already granted directory and persisting handles in IndexedDB; no additional file picker is needed. Folder reauthorization retains Task 1's direct-click, read-only picker. See [Chrome's File System Access guide](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access).

## Proposed Manager workflow

1. Open the legacy job using the existing supported Apply / Apply-this-page workflow. When an authorized documents response identifies recoverable missing cover-letter metadata, the paused Assisted Apply panel offers **Link existing PDFs**. Generic 404s, denied access, and local permission errors alone must not enable this action. Missing/revoked folder access still uses **Apply PDFs folder** and Task 2's Retry autofill.
2. The action opens the existing extension settings page with the current attempt ID. Runtime messages must validate the extension sender and the current owned Assisted Apply tab. Query parameters are identifiers, never authorization. On explicit opening, obtain fresh recovery context through the existing documents endpoint in an opt-in recovery-context mode. Ordinary documents success/error behavior remains compatible apart from replacing misleading regeneration guidance. Return no recovery details for unauthorized/nonrecoverable attempts, and use `Cache-Control: no-store` on all context responses.
3. Show server-authorized job ID, candidate, title/company, delivered-run identity, currently saved paths, and the exact recorded folder. Query the saved directory handle's permission. If it is missing/revoked, disable local selection and Save and explain how to authorize Downloads; do not prompt on page load. A new grant invalidates pending selections until the folder is reread.
4. Walk only the exact parent folder of the existing resume path, with no creation, recursive scan, filename synthesis, or filename normalization. List actual PDF file entries in that folder, with no preselected role. Require the Manager to explicitly select distinct resume and cover-letter entries, even if the saved resume name exists. Display complete relative filenames, including spaces and suffixes such as `Name (1).pdf` and `Name_Cover_Letter (2).pdf`. Different suffix numbers are valid; never infer one from the other.
5. Read only the two selected files locally. Require nonempty PDF bytes using the existing reader's validation, display filename/size and provide a local preview/open action, then require confirmation that these are the original resume and cover letter for the displayed candidate/job. Any preview is a view of the existing file bytes, not a document-generation operation. No text/content parsing or PDF rendering service is used. Escape filenames and job metadata as text in the UI.
6. **Save links** rechecks local read permission and reads both selected entries again. A read failure or changed selection/file during this confirmation invalidates Save; require renewed review. Send only the two exact relative paths plus attempt/run identity and the observed original paths as conflict preconditions. Do not send PDF bytes, Base64, absolute Windows paths, handles, or a list of other files.
7. Save success shows the confirmed paths and leaves Assisted Apply paused. The Manager explicitly uses existing **Retry autofill**, which calls the existing authorized documents endpoint and reads the files through the unchanged shared loader. Saving links never submits or automatically resumes filling. Cancel/Stop/lost claim disables further recovery and cannot resurrect the old panel/session. A save linearized before Cancel may have completed; explain that saved metadata remains but no filling resumes.

Existing resume metadata may name a download before Chrome added a suffix. Consequently, this operation may correct that filename **only as part of the explicit two-file confirmation**. It is not a general editor: the parent folder stays identical to the server's recorded resume parent, and the cover-letter path must initially be NULL/empty. Reject overwriting an already complete pair with different paths. Flat legacy `QTS_Resume/` folders are allowed, with the same explicit job/content confirmation; their names provide less assurance of association. Do not reconstruct folders from current names or timestamps.

If the recorded folder, original files, resume anchor, or delivered run is absent, stop with instructions to locate/restore the original files and contact the administrator. Do not search another folder, move/rename files, change job status, or enable Generation. Arbitrary relocation, missing-both-path recovery, and replacing a previously complete pair require a separate design.

## Proposed server contract and authorization

Use the current documents route for context and normal reads; add a narrowly scoped proposed `POST /api/extension/apply/documents/relink` for the approved write. Read relevant installed Next.js guides before implementing these routes. Use the existing extension token and browser headers via `authorizeApplyRequest`; do not trust role, Manager ID, browser ID, candidate ID, or filesystem permission claims from the payload.

Context and save must validate all of the following; repeat the mutable checks at the write boundary:

- Current unblocked signed-in Manager, current `canUseApply`, registered compatible browser, and the same Manager/browser owning the specified attempt.
- Attempt belongs to this job/candidate; job still belongs to that Manager, and its candidate still exists and meets current Apply availability rules (including not being blocked). Do not introduce a new candidate-assignment policy.
- Attempt is `waiting_review`, with an unexpired lease, no `submitGrantedAt`, and no finished state. Restrict the mutation to the Manager-held review state used by Assisted Apply; never mutate `submitting`, `waiting_confirmation`, terminal, foreign, or expired attempts.
- Job is still Generation-completed, not applied, has no bid using the existing `jobHasBid` rule, has the same safe nonempty resume anchor, and has the same latest delivered run belonging to the job/Manager. Reject an active Generation lease/run or a changed run; no Generation updates occur.
- Both paths are bounded, well-formed relative paths under `QTS_Resume/`, ending in distinct PDF entries in exactly the original resume parent folder. Reject traversal, absolute/drive/UNC paths, backslashes, controls, empty segments, and oversized payloads. Compare exact names, without decoding/normalizing them into different entries. Do not constrain names using today's candidate display name or guess numeric suffixes.

Perform the two path assignments atomically with compare-and-set preconditions on the original path pair and delivered-run identity. Lock/revalidate the attempt, job, and relevant Generation state in a consistent transaction order so Cancel, submit, reassignment, or a competing save cannot pass a stale authorization check. Use the database's time for lease validation. Determine the precise transaction mechanism from the installed database driver before implementation; multiple independent writes are unacceptable. A conflict returns a clear 409 and requires explicit context reload/review; never overwrite the winner automatically.

Set only `jobs.resume_local_path`, `jobs.cover_letter_local_path`, and conventional `jobs.updated_at`. Do not change generation status/error/leases, application history, attempt status/lease/evidence, candidate data, bids, templates, or document text. Replaying the same successful request for the same still-authorized job/run and identical saved pair returns success without an UPDATE; different requested paths conflict once the pair is complete. Validate ownership/state before that idempotent branch too. Record only operation identifiers through existing server logging; do not add a new audit table or repurpose attempt evidence. Durable path-edit auditing, if required, would be an additional approved schema decision.

The server cannot inspect the Manager's disk or prove a submitted path points to the historical generated document. The client cannot establish historical provenance from `%PDF-`, filenames, sizes, or a new hash when no original hash was recorded. Explicit Manager review is the trust boundary. A hostile authorized client can mislabel files; this design does not claim otherwise. Local previews and reads never create replacement files, and Apply uploads the bytes found at the explicitly confirmed paths. External edits after relinking remain possible under the existing local-file model; cryptographic immutability would need a separate fingerprint protocol/schema design.

## Separate Chrome profiles and Auto Apply

Only the relative path pair is shared through the job record. Each Chrome profile must independently authorize the **same physical Downloads folder** through Task 1 and retain its own extension-origin handle. Never synchronize handles, tokens, browser keys, or OS grants. Profile B must obtain its own owned attempt after profile A releases the existing one; the one-live-attempt-per-job index remains intact. Normal authorized documents loading then resolves the same shared filenames without a second relink/write. Different absolute root locations are acceptable only when they expose the intended same document tree. Choosing an unrelated Downloads tree with similarly named files cannot establish provenance.

Auto Apply remains unattended and does not choose files or hold a new recovery dialog. If it stops/releases a legacy job on missing paths, stop Auto Apply, open that job in supported Assisted Apply, relink under its normal owned review attempt, and either continue there or Cancel that review before restarting Auto Apply. The existing Auto Apply release/selection rules remain authoritative; recovery never resets failed/skipped/applied states or makes excluded jobs eligible. If the normal work selector still excludes a job, report that separately rather than bypassing it. Both modes subsequently use the same authorized canonical paths and shared local reader.

## Request budget, migrations, and release dependencies

There is no background discovery, recovery polling, per-file Vercel request, PDF upload to QTS, or batch backfill. The normal failing documents request already exists. Recovery adds one context GET on explicit opening and one metadata POST on confirmed Save. The existing explicit Retry adds its normal documents GET; retain it to revalidate the attempt. Local selection/preview changes cause zero requests/writes. Existing session/permission checks and claim heartbeats continue; recovery does not add a heartbeat or renew a claim on its own. Debounce Save; network timeout permits only an explicit identical retry, handled idempotently. No automatic database write occurs on page load or selection.

No additional migration is proposed beyond the already pending nullable column in 0088. Do not apply 0088 here: independently verify Production identity, predecessors and migration ledger in Task 7, then obtain explicit migration approval. The earlier configured-database findings are historical, not a current Production audit. Do not deploy column-dependent code ahead of the approved schema rollout. Task 4 must version/gate the recovery protocol as well as the new finalize/documents protocols without disabling unrelated workflows. Rollback may disable relinking while retaining valid saved paths; never roll back by deleting PDFs or resetting completed jobs.

## Acceptance criteria and implementation test matrix

| Case | Required assertion |
| --- | --- |
| Normal legacy recovery | Eligible completed job, existing resume anchor, NULL cover path, delivered run and live owned review: explicit two-file selection saves exact paths in one atomic job update; completed status and all unrelated records remain unchanged. |
| Chrome uniquification / historical names | Multiple plausible files with independent suffixes, spaces and historical candidate names remain unselected; only the Manager's exact choices are saved. Explicitly corrected resume suffix is permitted in the same parent. |
| Local byte preservation | Hash fixture originals before recovery and compare actual uploaded bytes in both modes after recovery, including after worker restart. Assert zero Generation, render, print, new-download, filesystem-write or document-content API calls. Preview uses original bytes only. |
| Access control | Missing/expired token, blocked Manager/candidate, disabled Apply, bad browser identity, incompatible version, foreign Manager/browser/attempt, reassigned job/candidate, missing/foreign delivered run: no recovery details leaked and zero updates. |
| Attempt state | Expired/null lease, Cancel/Stop, removed job, submit granted, submitting, waiting confirmation and all terminal states reject Save. Ordinary documents authorization remains enforced. |
| Invalid local inputs | Missing grant, permission revoked before listing/read/Save, missing folder/file, empty/non-PDF, same file for both roles, changed file after confirmation: clear instructions, no write or automatic retry, no alternative-file selection. Reauthorization requires renewed confirmation. |
| Path boundary | Traversal, slash/backslash tricks, drive/UNC/absolute paths, controls, huge payload, different parent and manually forged paths are rejected server-side. Valid flat legacy parent is supported without reconstructing today's structure. |
| Conflicts / concurrency | Competing saves, changed paths/run, concurrent reassignment/Generation, Cancel/submit racing Save: transactional authorization/CAS prevents stale writes. Identical retry after response loss performs no second UPDATE. No new attempt or state reset is hidden in recovery. |
| User interaction / lifecycle | Manager access only, legacy feature disabled; opening does not select/save. Closing, denied grant and canceled confirmation make no change. Success remains paused until explicit Retry; late results after Cancel do not resume or restore a panel. Repeat context reads do not mutate records. |
| Two real Chrome profiles | Two independently granted profiles read one real shared filesystem fixture, serial owned claims, same canonical paths and identical uploads. B performs no relink and cannot use A's grant/attempt. A similarly named separate folder is not silently selected. OPFS fixtures alone do not prove cross-profile shared-disk behavior; include an actual shared-folder browser/manual acceptance check and report native consent automation limits. |
| Auto Apply recovery | Missing metadata stops/releases through existing behavior; recover in owned Assisted Apply, release normally, then eligible Auto Apply reads the saved pair with original bytes. No automated file choice, new eligibility, or job-state reset. |
| Unsupported legacy rows | Missing both paths, missing delivered run/anchor/folder, applied/bid job or already complete different pair receives a bounded explanation, no regeneration/backfill/overwrite. |
| Cost and regression | Count only explicit context/save/retry requests; zero per-selection/content requests, single metadata update, idempotent replay. Run Task 1 folder/original-byte and Task 2 pause/retry/cancellation regressions; run affected browser cases serially, then typecheck, changed-source lint and diff checks. Keep known Task 6 baseline failures separate. |
